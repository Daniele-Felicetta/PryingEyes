# Building, shipping and CI

How the game is built, where the builds go, how a change reaches `preview` and how the gate on GitHub fits in.
Checked against `Editor/BuildPlayer.cs`, `tools/ship.ps1`, `.github/workflows/gate.yml` and `AGENTS.md` on 2026-11-15.
What is verified by running things is in [testing.md](testing.md); why the suite is split the way it is, in
[suite-architecture.md](suite-architecture.md).

## The project

- Unity **6000.6.7f1** (`unity/PryingEyes/ProjectSettings/ProjectVersion.txt`). Install the platform modules you need from the same
  version in Unity Hub.
- The only scene of the player is `Assets/_PryingEyes/Scenes/Torre.unity` (the Tower, see [../game/tower.md](../game/tower.md)). The classic
  hall (`Hotel.unity`, `HotelBuilder`) stays in the project, outside the build.
- To play from the editor: open `unity/PryingEyes`, open `Torre.unity`, press Play. Floors are generated at run time from a seed.

## Build methods

Run from the repository root; Unity must not have the project open (one editor per project):

```powershell
Unity.exe -batchmode -projectPath unity/PryingEyes -executeMethod PryingEyes.EditorTools.BuildPlayer.Torre -buildOut <folder> -quit
```

`PryingEyes.EditorTools.BuildPlayer` (`Assets/_PryingEyes/Editor/BuildPlayer.cs`):

| Method | What it does |
| --- | --- |
| `Torre` | Regenerates the Tower scene and its material and prefab kits (`TorreBuilder`), then builds the Windows player. No lightmap bake. |
| `Torre` with `-scriptsOnly` | When `<folder>` already holds a full build, recompiles only the scripts (`BuildOptions.BuildScriptsOnly`): about 2 MB are written instead of the ~700 MB of a full build. Use a full build when models, textures, prefabs, materials or scene components changed. |
| `Windows` | The same Windows player without regenerating the scene and the kits. |
| `Web` | WebGL build of the Tower into `Builds/Web`. Long procedural sounds are generated while loading, because WebGL has no C# threads. |
| `City` | The experimental city as a separate executable in `Builds/CityPreview` (or `-buildOut`); `Citta.unity` is regenerated by `CityBuilder` unless `-scriptsOnly` finds it. See [city-prototype.md](city-prototype.md). |
| `All`, `Verify`, `Everything` | Legacy: the classic hall, its screenshots and audio export. |

Flags:

- `-buildOut <folder>` writes `<folder>/PryingEyes.exe`. **Without it the build overwrites `Builds/PryingEyes.exe`, the game the
  maintainer plays.** Always pass it for verification builds (`ship.ps1` and the studio do).
- `-distribution` defines `PE_DISTRIBUTION_BUILD`, which compiles out the files wrapped in `#if !PE_DISTRIBUTION_BUILD`: 29 of the 42
  `*Test*.cs` files in `Scripts/` and the trailer recorder (`TrailerCapture.cs`, `TrailerJob.cs`, `FloorDirector.Trailer.cs`, and a part of
  `FloorDirector.cs`). Not wrapped, so still in the player: the `ArchitectureTest*`, `CityTest*`, `CoopTest*` and `StealthTest*` files
  (counted by grep on 2026-11-15). It needs a full build: with `-scriptsOnly` the method logs an error and exits with 2.
  A distribution build also runs `BuildScrub` (`Editor/BuildScrub.cs`). The compiler writes the path of the `.pdb` it produced into every
  assembly, which names the folders of the build machine, so that entry is overwritten with the bare file name; then every managed assembly
  of the build is searched for the path of the checkout and each hit is logged as a warning (`[PryingEyes] distribution: ...`).

The methods that build a player (`Torre`, `Windows`, `Web`, `City`) exit with 2 when the build does not succeed.

## Where builds live

`unity/PryingEyes/Builds` is git-ignored and holds:

| Path | Role |
| --- | --- |
| `PryingEyes.exe` with `PryingEyes_Data`, `UnityPlayer.dll`, `D3D12` and `MonoBleedingEdge` at the top level | The game the maintainer plays (taskbar and Start menu shortcuts). It must always be the latest build; `tools/ship.ps1` refreshes it after every build and writes `build_info.json` next to it (commit, date, build mode, uncommitted sources it contains). Never close the game to update it. |
| `Audit/` | Where builds and checks run. Tests and agents use it, never the top-level game: a running player locks its files. |
| `CityPreview/` | Where the studio publishes the city prototype. |
| `Releases/` | The released zips. |
| anything else (`*Candidate`, `Web`, per-release folders) | Disposable. Delete it when the task ends. The `build/` folder of a finished studio job (`unity_logs/studio/*/build`, about 700 MB each) is disposable too; its report and logs are the record. |

A full build rewrites about 700 MB. Prefer `-scriptsOnly`, and do not rebuild just to look: disk space and write bandwidth are the scarce
resources on the maintainer's machine.

## Shipping a change: `tools/ship.ps1`

One script does commit, build, smoke test, push and the refresh of the maintainer's game, with the checks and the traps already solved.
Its header (in Italian) is the full reference; this is the shape of it.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ship.ps1 -Detach -MessageFile msg.txt -Paths "a/b.cs,c/d.md"
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ship.ps1 -Wait 540     # repeat until it prints SHIP: OK or SHIP: FALLITO
```

| Step | What it does |
| --- | --- |
| checks | Right branch, Unity not open on the project, no copy of the game running from the build folder. |
| gate | `tools/check_suite.py` and the Python unit tests (about a minute, no Unity). A failure commits nothing. `-NoGate` skips it. |
| commit | Only the paths of `-Paths` (never `git add -A`), message from `-MessageFile`, starting from an empty index. A `Co-Authored-By` trailer is appended when missing. Without `-Paths` nothing is committed. |
| sources | Unity builds the working tree, not the commit. After committing, the script lists the uncommitted sources the build will contain (files under `unity/PryingEyes/{Assets,Packages,ProjectSettings}` that differ from `HEAD`, derived files and line-ending-only changes excluded). It never blocks on a dirty tree; the list goes into the summary, a warning, `unity_logs/ship_built.json` and `Builds/build_info.json`. `-RequireClean` refuses instead: for releases. |
| build | Unity in batch mode at low priority into `Builds/Audit` (`-OutDir` to change it). `-Mode auto` builds in full when a file other than `.cs` changed since the last ship, otherwise scripts only; `full` and `scripts` force one. |
| smoke | `tools/check_navigation.py` on `-SmokeFloors` floors (seed `-SmokeSeed`), no graphics. A failure stops before the push. |
| push | `origin <current branch>`, never forced, with the settings for large files; then checks that the remote has the same `HEAD`. |
| game | Copies the build into `Builds/`, only when the maintainer's game is closed. When it is open the script starts a hidden process that waits for it to close and copies then (`-DeferExeMin`, 720 minutes by default, 0 turns it off). `-RefreshOnly` does just this step. |

Logs and markers are in `unity_logs/`: `ship_last.log` and `ship_last.status`, `ship_build.log`, `ship_built.json`, `ship_refresh.log` and
`ship_refresh.status`. The exit code is 0 only with `SHIP: OK`. `-DryRun` rehearses without changing anything. The script is ASCII on
purpose: PowerShell 5.1 misreads accents in a file without a BOM.

A change that touches no game source (documentation, tools) can be shipped with `-Mode scripts`: the build is then a two-megabyte
recompile, and the game keeps the data of the last full build.

## The gate

The gate is the set of checks that must pass before a change counts as done:

1. `python tools/check_suite.py`: the boundaries of the reusable packages and engine, and the documentation (links, index, no
   machine-specific paths).
2. `python -m unittest discover -s tools -p "test_*.py"`: the hermetic unit suite.
3. `python tools/studio.py test weapon-state`, `python tools/studio.py test survival` and `python tools/studio.py test economy`: the three .NET rule labs.

`ship.ps1` runs the first two before every commit. The third needs the project lock, which fails with `PROJECT_BUSY` while another
agent has a production running, so it only runs on GitHub: `.github/workflows/gate.yml` runs all three on every push to `preview` and every
pull request against it, on a Windows runner, from a sparse checkout of a few MB (the `sparse-checkout` block of the workflow lists the
only paths the gate reads: add a path there when a check starts reading a new one). The lab reports are kept as the `lab-reports`
artifact. There is no branch protection (`ship.ps1` pushes straight to `preview`), so the gate reports rather than blocks: look at the
latest run before starting work (`gh run list --branch preview --limit 1`) and fix a red one first.

## Branches and worktrees

`preview` is the only long-lived branch. Anything else goes through a pull request and is deleted as soon as it merges (a squash merge makes
git call the branch unmerged: delete it anyway, its commits stay on the pull request). One agent writes at a time in the checkout the
editor opens; anyone who does not need the editor works in a separate worktree on its own branch (`git worktree add`), and removes it with
`git worktree remove` when the task ends.

## Other platforms

The Windows player is the one that is built and tested. The others are set up but unproven:

- **Web**: install Web Build Support, then Build and Run to try it, or upload the whole output folder to an HTTP server configured for the
  chosen compression. `BuildPlayer.Web` writes `Builds/Web`.
- **iOS**: install iOS Build Support, pick iOS in Build Profiles and build. Open the generated project on a Mac with Xcode, set a unique bundle
  identifier, the team and the signing, then build and install on the device. Distribution needs the right Apple credentials.
- **Android**: install Android Build Support with the SDK, NDK and OpenJDK, then build an APK to try it or a signed AAB for Google Play.

Touch controls (iOS, Android, and the Web build when it detects a mobile browser) are described in
[../game/tower.md](../game/tower.md#touch-controls). Controls and performance have not been tried or tuned on real devices.

## Releases

A release is a zip of a full **distribution** build attached to a GitHub release. It is made only on request. The version is
`bundleVersion` in `unity/PryingEyes/ProjectSettings/ProjectSettings.asset` (Player Settings > Version, `x.y.z`): the menu shows it
([../game/display-and-menu.md](../game/display-and-menu.md#version-label)), the tag is `v<version>` and the zip is
`PryingEyes-v<version>-Windows-x64.zip`.

1. Bump `bundleVersion` in a commit and ship it with `tools/ship.ps1 -Mode full` (a project setting changed, and a scripts-only build would keep
   the old number inside the player). Wait for the green run of the gate on GitHub: the tag goes on that commit.
2. `powershell -NoProfile -ExecutionPolicy Bypass -File tools\release.ps1 -Version <version>` does the mechanical part (about five minutes) and
   stops at the first problem. The steps can be run alone with `-Step`; the header of the script is the full reference.
   - `check`: `bundleVersion` equals the version asked for; the branch is `preview` and `HEAD` is `origin/preview` (a release is made from a
     pushed commit); no uncommitted source under `Assets`, `Packages` or `ProjectSettings` (the test of `ship.ps1 -RequireClean`: derived files and
     line-ending-only changes do not count); Unity is installed and not open on the project; `tools/release/LEGGIMI.txt` exists;
     `Builds/Release-v<version>` does not exist yet.
   - `build`: Unity in batch mode at low priority, `BuildPlayer.Windows -distribution` into `Builds/Release-v<version>` (outside `Audit`;
     `ship.ps1` never passes `-distribution`). It needs `Build result: Succeeded`, no compile error, `0 still contain the checkout path` from
     `BuildScrub`, and still no uncommitted source. It leaves `unity_logs/release_v<version>.json` with the commit it built; the other steps start
     from there.
   - `scan`: searches every file that will be zipped for the repository folder and the user folder of this PC, with both kinds of slash, in
     UTF-8 and in UTF-16. `BuildScrub` covers only the managed assemblies. For 0.6.2 the only file that named them was `lib_burst_generated.txt` in
     the `*_BackUpThisFolder_ButDontShipItWithYourGame` folder, which the zip leaves out.
   - `zip`: `Builds/Releases/PryingEyes-v<version>-Windows-x64.zip` with the files at its root and `LEGGIMI.txt` added (from
     `tools/release/LEGGIMI.txt`, with `{VERSION}` and `{COMMIT}` filled in), without the `*_BackUpThisFolder_ButDontShipItWithYourGame` and
     `*_BurstDebugInformation_DoNotShip` folders; then the hash of every entry against its source file, and
     `Builds/Releases/v<version>/SHA256SUMS.txt`. It never overwrites a zip.
   - `smoke`: the packaged player without graphics (`-batchmode -nographics`), 35 seconds each: the menu, the menu with `-padauto`, and the split
     screen at 2, 3 and 4 players (`-splitscreen N -menureview -nowaves`, so that the saved display setting is not applied and no wave starts).
     The player log must have `[PryingEyes] VERSIONE <version>`, for the split screen `[PryingEyes] split: N giocatori`, and no exception. It runs
     after the zip because running the player can add files to the folder. It opens no window, and `-batchmode` and `-menureview` both keep the
     game from applying or saving the display settings (`VideoSettings.Automated`).

   The package has no test classes (`-distribution`), so the in-game suites run on the `Audit` build of the same commit, not on the package. A
   window run would take the screen and the display registry values: say in the notes when it was not done on the package.
3. Write the notes (Italian, without accents, like the previous ones): what changed, what was tested and on which build, and what was not. Then
   `gh release create v<version> <zip> <sums> --target <full sha of the built commit> --title ... --notes-file ... --draft`, check the name, size
   and digest of both assets on the draft, and publish it as the latest release with
   `gh api -X PATCH repos/<owner>/<repo>/releases/<id> -F draft=false -f make_latest=true`.
4. Delete `Builds/Release-v<version>` once the zip is verified: it can be rebuilt and the zip holds its content.

`tools/release.ps1` publishes nothing: the draft and the publication stay manual on purpose. `tools/test_release.py` runs the real script on
throwaway repositories and fake build folders (the checks, the search for paths and the zip); the build and smoke steps are acceptance checks on
the real project, which is what running the script is. The scripts of the 0.6.2 release were the first version of this tool.
